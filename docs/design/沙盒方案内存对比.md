# 沙盒方案内存对比

> 七方代码执行/沙盒隔离方案的内存占用与部署复杂度横向对比
> 测试时间：2026-04-29

## 测试环境

- 主机：Ubuntu 24.04 LTS, x86_64, 16核, 15GB RAM
- Docker：已安装，配置国内镜像加速
- KSM：未启用

## 关键发现

### 1. 内存开销层级分明

| 梯队 | 内存范围 | 代表方案 | 说明 |
|------|---------|---------|------|
| 第一梯队 | <5MB | sandbox (Go) | Go 静态链接二进制运行在 Docker 中，极致轻量，牺牲多语言支持 |
| 第二梯队 | 15-20MB | Docker、OpenSandbox | OpenSandbox 比纯 Docker 高约 20%，来自编排层额外开销 |
| 第三梯队 | 75-85MB | CubeSandbox Alpine、microsandbox | VM 级隔离轻量方案；Alpine 极简 Guest OS，microsandbox 是 libkrun 固有空载 |
| 第四梯队 | 350-650MB | CubeSandbox Ubuntu | 完整 systemd + 全套服务，启动后 25-30 秒才能稳定 |

### 2. CubeSandbox Ubuntu 非线性增长根因

Guest OS（Ubuntu + systemd）启动不是瞬间完成的，内核初始化页表、启动服务需要 25-30 秒，期间内存持续增长。换 Alpine 后内存从 359MB 降到 76MB，省了 79%。

## 选型建议

| 场景 | 推荐方案 | 理由 |
|------|---------|------|
| 极致密度、单语言 | sandbox (Go) | 2MB/实例，5000+ 并发 |
| 通用代码执行、低隔离要求 | Docker / OpenSandbox | 15-18MB/实例，简单直接 |
| 需要 VM 级隔离、快速启动 | microsandbox | 83MB/实例，<5s 启动 |
| 需要 VM 级隔离、极小镜像 | CubeSandbox Alpine | 76MB/实例，可控 |
| 需要完整 Linux 环境 | CubeSandbox Ubuntu | 359MB+/实例，功能完整 |

## OpenSandbox 评估结论

- **定位**：不是 VMM，而是沙盒编排平台。默认 docker runtime 等同于标准 Docker 容器
- **内存**：docker runtime 下单实例 ~18MB，与纯 Docker 基本一致
- **部署复杂度**：Server 依赖 Python 3.12+、Docker、阿里云镜像；存在异步代码调用同步 docker pull 阻塞事件循环的已知 bug
- **适用场景**：需要沙盒编排层（生命周期管理、网络策略、多租户）但不想自建的平台
