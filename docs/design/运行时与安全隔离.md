# sandbox 运行时与安全隔离

> 更新时间：2026-05-11
> 关注对象：`claw` 运行时容器、`sandbox-go` 安全约束、workspace 边界

## 一、功能定位

`sandbox`（`claw`）是**独立执行面服务**，负责承载 Clone（数字分身）的实际运行循环：

- 单 clone 的 tool dispatch 与执行
- Python / Node / Shell 脚本运行
- SSE 事件输出（`text_delta`、`tool_call_start`、`tool_call_output`、`done` 等）

`sandbox-go` 是容器内第二层安全约束，不是唯一安全边界：

- **资源限制**：cgroup v2（CPU、内存、进程数、磁盘配额）
- **网络隔离**：`sandbox-go` 强隔离路径（netns + veth + SOCKS5 代理 + IP 黑名单）
- **文件系统隔离**：workspace 只挂当前 clone 目录，不挂宿主敏感目录

核心原则：

| 原则 | 说明 |
|------|------|
| 一个 clone 一个容器 | 同一 clone 同时最多一个活跃容器 |
| Session 驱动启停 | Session 开始时启动，结束时关闭 |
| workspace 持久化 | 宿主持久目录挂载，容器销毁后保留 |
| 控制面不丢真相源 | `claw` 可被销毁重建，主状态始终在外部服务 + DB |

## 二、通信协议

外部调用方与 `claw` 之间使用 **HTTP + SSE**：

| 接口 | 方法 | 用途 |
|------|------|------|
| `GET /readyz` | GET | 探活，确认 claw 已就绪 |
| `POST /runtime/start` | POST | 初始化 runtime 执行上下文 |
| `POST /runtime/turn` | POST | 投递一轮用户输入或 tool result |
| `GET /runtime/stream?sessionID=...` | GET | SSE 拉取执行事件流 |
| `POST /runtime/stop` | POST | 主动结束 runtime |
| `GET /runtime/status` | GET | 查看 runtime 当前状态 |

SSE 事件类型：

- `runtime_started`
- `text_delta`
- `tool_call_start`
- `tool_call_output`
- `tool_call_end`
- `runtime_error`
- `done`

## 三、Workspace 挂载规则

**Workspace 路径规则：**

```text
宿主机:  <WorkspaceRoot>/<agentID>/
容器内: /workspace
```

**强约束：**

- 容器宿主侧 **只能** bind mount 到该 clone 的具体目录
- **不允许** 把整个 workspace 根目录挂进去
- 原因：防止同容器内进程枚举并访问其他 clone 的工作目录

**当前挂载清单（v1）：**

| 宿主路径 | 容器路径 | 说明 |
|----------|----------|------|
| `<WorkspaceRoot>/<agentID>/` | `/workspace` | clone 工作目录 |
| `<ControlRoot>/<agentID>/` | `/runtime/control` | 控制面通信目录 |
| `<MappedSkillRoot>/` | `/opt/skills/mapped` | mapped 技能资产（可选） |
| `<SharedSkillRoot>/` | `/opt/skills/shared` | shared 技能资产（可选） |
| `<CommonSkillRoot>/` | `/opt/skills-store/common` | common 技能资产（可选） |

**不挂载（安全要求）：**

- `docker.sock`
- 宿主任意敏感目录
- 其他 clone 的 workspace

## 四、资源限制模型

### 4.1 Sandbox 内部单任务限制

**资源限制策略（cgroup v2 优先，prlimit 降级）：**

| 资源 | 默认值 | 限制方式 | 说明 |
|------|--------|----------|------|
| CPU | 25%（0.25 核） | `cpu.max`（cgroup） | Docker 环境下 cgroup 不可写，依赖容器级 `NanoCPUs` 兜底 |
| 内存 | 256 MB | `memory.max`（cgroup）→ `prlimit --as`（降级） | cgroup 不可写时自动降级为 prlimit `--as` |
| 进程数 | 32 | `pids.max`（cgroup）→ `prlimit --nproc`（降级） | cgroup 不可写时自动降级为 prlimit `--nproc` |
| 单文件大小 | 100 MB | — | — |
| workspace 总大小 | 1 GB | — | — |
| 超时 | 300 秒 | — | — |

> **取值依据**：10 并发场景下，单任务 0.25核/256MB/32进程，总和约 2.5核/2.56GB/320进程，需由 Docker 容器整体限制兜底。
>
> **降级机制**：启动任务时检测 `/sys/fs/cgroup` 可写性。不可写（如 Docker cgroup v2）时，自动将命令包装为 `prlimit --as=<内存> --nproc=<进程数> -- <原命令>`。非 Docker 环境（K8s、裸机）中 cgroup 可写时仍优先使用 cgroup v2。

### 4.2 Docker 容器整体限制

创建 claw 容器时，通过 `HostConfig` 施加整体资源上限：

| 资源 | 默认值 | 配置字段 | 说明 |
|------|--------|----------|------|
| 内存 | 3072 MB | `ContainerMemoryMB` | 硬限制，超限时 OOM |
| CPU | 200%（2 核） | `ContainerCPUQuota` | 百分比，200 = 2 核 |
| 进程数 | 512 | `ContainerPidsLimit` | 防容器内 fork bomb |

### 4.3 115 环境实测数据

测试命令：`perl` 计算密集型循环（`sqrt` 迭代，每个任务持续 6~8 秒）

| 场景 | CPU 峰值 | 内存峰值 | PID 峰值 | 说明 |
|------|---------|---------|---------|------|
| **静止** | 0% | 6.55 MiB | 8 | 基础开销 |
| **1 任务** | **101.61%** | 7.40 MiB | 10 | 单任务近满 1 核 |
| **10 并发** | **202.54%** | 15.45 MiB | 38 | 10 任务并发，吃满 2 核 |

**关键发现：**

1. **并发改造生效**：10 任务同时提交后 CPU 达到 202%，证明 10 个任务确实并发执行，而非串行排队
2. **内存开销极低**：10 并发仅增加约 9 MiB 内存，PID 从 8 增至 38
3. **Sandbox 内部 cgroup 限制在 Docker 环境下无法生效，已降级为 prlimit**：单任务 CPU 达到 101%，远超配置的 0.25核（25%）限制。
   - **根因**：Docker 的 cgroup v2 实现中，容器内的 `/sys/fs/cgroup` 为只读挂载，即使添加 `--privileged` 或 `-v /sys/fs/cgroup:/sys/fs/cgroup:rw` 也无法改变。`ResourceLimiter.Apply` 创建子 cgroup 时 `os.Mkdir` 返回 `EROFS`（Read-only file system）。
   - **降级方案**：`executeCommand` 中检测 cgroup 可写性，不可写时自动将命令包装为 `prlimit --as=<内存字节> --nproc=<进程数> -- <原命令>`。prlimit 限制的是虚拟地址空间（`RLIMIT_AS`）和 UID 级进程数（`RLIMIT_NPROC`）。
   - **CPU 限制**：prlimit 的 `--cpu` 限制的是 CPU 时间（秒），不是使用率百分比，因此 CPU 限制仍依赖 Docker 容器级 `NanoCPUs`（2核）兜底。
   - **影响**：内存和进程数有任务级隔离（prlimit），CPU 无任务级隔离（依赖容器级 2核），单个任务仍可能抢占全部 CPU。
   - **缓解**：依赖 Docker 容器整体限制（2核/3GB/512进程）作为兜底，防止影响宿主机。非 Docker 环境（K8s、裸机）中 cgroup 可写时仍优先使用 cgroup v2。

**运行环境要求：**

| 模式 | 权限要求 | 资源限制 | 网络隔离 |
|------|----------|----------|----------|
| 标准模式 | root / CAP_NET_ADMIN + CAP_SYS_ADMIN | Docker 容器级限制 + prlimit 降级（内存/进程）；cgroup v2 在非 Docker 环境可用 | **强制启用** netns + veth + SOCKS5 |
| 降级模式 | 无特殊权限 | Docker 容器级限制 + prlimit 降级（内存/进程） | 环境变量注入代理（紧急关闭网络隔离时） |

## 五、网络边界

**Docker 网络模式要求：**

`claw` 容器必须与外部服务容器位于**同一个 Docker 网络**（通过 `NetworkMode` 配置），原因：

- 技能需要通过服务名（如 `allinone:7777`、`emqx:18083`）访问内部服务
- Docker 默认 `bridge` 网络中的容器无法解析 docker-compose 自定义网络的服务名
- 不同网络之间互相隔离

**当前 v1 容器默认网络行为：**

- 宿主已发布的端口（如 PostgreSQL `5432`、Redis `6379`）**默认可访问**
- 公网 **默认可达**
- 私网地址在当前 Docker 网络下可能不可达，但这**不代表策略已隔离**

**sandbox-go 强隔离路径（需要 root + CAP_NET_ADMIN）：**

```
claw main process          → 默认网络（可访问外部服务）
sandboxed task process tree → 受限 netns（只能访问 SOCKS5 代理口）
                              → 以 runner UID/GID（10001）运行，无法修改 iptables
```

**子进程权限隔离：**

- `CLONE_NEWNET` 在 fork 时创建新 netns（此时子进程仍有 root caps）
- `Credential` 在 exec 前将 UID/GID 降到 runner（10001）
- runner 用户无法执行 `iptables`（需要 root），无法清空 OUTPUT DROP 规则
- 即使原始 socket 也无法绕过 OUTPUT DROP（`sendto` 返回 `EPERM`）

**IP 黑名单（sandbox-go 拦截）：**

```text
IPv4:
- 10.0.0.0/8        # 私有 Class A
- 172.16.0.0/12     # 私有 Class B
- 192.168.0.0/16    # 私有 Class C
- 127.0.0.0/8       # 回环
- 169.254.0.0/16    # 链路本地（云元数据）
- 0.0.0.0/8         # 本网络
- 224.0.0.0/4       # 组播
- 240.0.0.0/4       # 保留

IPv6:
- ::1/128           # 回环
- fc00::/7          # 唯一本地
- fe80::/10         # 链路本地
- ff00::/8          # 组播
```

**出站协议控制：**

`sandbox-go` 强隔离路径下，子进程 netns 内配置以下 iptables OUTPUT 策略：

| 规则 | 动作 | 说明 |
|------|------|------|
| `-P OUTPUT DROP` | 默认丢弃 | 所有出站流量默认拒绝 |
| `-o lo -j ACCEPT` | 允许回环 | lo 接口通信不受限 |
| `-m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT` | 允许响应 | 已建立连接的返回流量 |
| `-d <BridgeIP> -p tcp --dport <ProxyPort> -j ACCEPT` | 允许代理 | 仅允许访问 SOCKS5 代理 |
| `-p udp -j DROP` | 丢弃 UDP | **显式禁用 UDP 出站** |

> 原始 socket（`SOCK_RAW`）尝试直接发包时，`sendto` 返回 `EPERM`，无法绕过 OUTPUT DROP。

**当前结论：**

- **网络隔离为强制安全要求，默认启用**。`CLAW_ENABLE_SANDBOX_NET` 环境变量仅用于紧急关闭（如排障时）
- 强隔离路径下，任务进程以 runner UID 运行，无法篡改 iptables 规则
- 如需 runtime 不能碰宿主内部服务、只能走受控代理访问公网，必须额外配置网络策略

## 七、安全边界总结

### 7.1 已验证的防护

| 攻击类型 | 防护机制 | 状态 |
|---------|---------|------|
| 未挂载宿主目录访问 | bind mount 最小化 | 已验证 |
| docker.sock 滥用 | 不挂载 docker.sock | 已验证 |
| 只读目录写入 | 只读 bind mount | 已验证 |
| CPU 爆炸 | cgroup `cpu.max` / Docker `NanoCPUs` | 无任务级 CPU 限制（prlimit `--cpu` 限制的是时间秒数），依赖容器级 2核兜底 |
| 内存爆炸 | cgroup `memory.max` → prlimit `--as` | prlimit 降级生效（`RLIMIT_AS` 限制虚拟地址空间） |
| Fork bomb | cgroup `pids.max` → prlimit `--nproc` | prlimit 降级生效（`RLIMIT_NPROC` 限制 UID 级进程数） |
| 云元数据泄露 | `169.254.169.254` 黑名单 | 已实现 |
| 内网访问（强隔离路径） | SOCKS5 + IP 过滤 | 已实现 |
| UDP 出站绕过 | iptables OUTPUT DROP + 显式 UDP DROP | 已验证（原始 socket 无法绕过） |
| iptables 规则篡改 | 子进程降权到 runner UID（10001）| 已验证（runner 无法执行 iptables） |

### 7.2 当前已知限制

| 限制 | 影响 | 缓解措施 |
|------|------|----------|
| 宿主已发布端口默认可访问 | 无 sandbox-go 时容器可连宿主服务 | **sandbox-go 强制启用后已阻断**（OUTPUT DROP） |
| 公网默认可达 | 无 sandbox-go 时容器可出公网 | **sandbox-go 强制启用后已阻断**（仅允许 SOCKS5 代理口） |
| workspace 容量无统一配额 | 单个 clone 可写满磁盘 | 依赖宿主目录 quota |
| 容器 rootfs 可读 | 可读取 `/etc/passwd` 等 | 后续收紧 rootfs |

### 7.3 漏洞修复记录

| 漏洞 | 等级 | 修复方式 | 提交 |
|------|------|----------|------|
| `BuildSkillEnv` 向子进程注入长期 AK/SK 凭证 | **高危** | 预生成 1 小时 JWT，只注入 `UR_TOKEN`；JWT 生成失败时降级回 AK/SK | — |
| 网络隔离时子进程保持 root，可 `iptables -F` 清空规则 | **高危** | `CLONE_NEWNET + Credential` 同时设置，fork 后 exec 前降权到 runner UID | `7931bf68d` |
| 原始 socket / UDP 绕过 OUTPUT DROP | **中危** | 显式添加 `-p udp -j DROP` | `a3f0ad349` |
| 子进程继承全部环境变量，可能泄露敏感信息 | **高危** | `buildSafeEnv()` 白名单模式，只传递 PATH/HOME/CLAW_*/locale/timezone | `3646ceac9` |
| prlimit `--nproc` UID 级全局共享，跨容器影响 | **中危** | Docker 环境下跳过 `--nproc`，依赖容器级 PidsLimit（512）兜底 | `995d8ad5d` |
| 网络隔离默认关闭，需手动启用 | **高危** | `EnableSandboxNet` 默认 `true`，环境变量仅用于紧急关闭 | `28e3f8635` |
| GenerateUniqueIPs IP 溢出/冲突 | **中危** | 使用相邻对分配 (2,3),(4,5)...(252,253)，避免无效/冲突地址 | `08cd9520e` |
| stdout/stderr 无大小限制导致 OOM | **高危** | 每流限制 10MB，`limitWriter` 截断超额输出 | `a25fedf22` |
| 并发任务无限制导致资源耗尽 | **中危** | 并发任务上限 32 | `a25fedf22` |
| 任务超时无上限 | **低危** | 默认 5 分钟，最大 30 分钟 | `a25fedf22` |

### 7.4 低优先级问题（已缓解）

| 问题 | 影响 | 当前状态 |
|------|------|----------|
| /tmp 目录共享 | 同一容器内多个任务共享 /tmp | 同一 clone 信任域内，风险可控 |
| veth 异常残留 | SIGKILL 时 networkCleanup 可能不执行 | veth 名称含 PID，不会无限增长；不影响安全 |
| 无任务级 CPU 限制 | 单个任务可占满容器 2 核 | Docker `NanoCPUs` 兜底 |
| skill_guard 只检查 mapped skill | shared/common skill 和 shell 命令未静态分析 | 设计限制，动态 shell 命令难以静态检查 |
| 容器内二进制（ur-api 等）可执行 | runner 可运行这些二进制 | 环境变量已白名单化，缺少配置则无法工作 |

### 7.5 待修复漏洞

| 漏洞 | 等级 | 说明 | 修复方案 |
|------|------|------|----------|
| **HTTP API 无认证** | **严重** | `/runtime/exec` 等 API 没有任何认证，同 Docker 网络的任何容器都可执行任意命令 | 添加共享密钥认证（如 `X-Claw-Token`），外部调用时携带 |

### 7.6 后续增强方向

1. **API 认证**：为 claw HTTP API 添加共享密钥或 JWT 认证
2. **磁盘配额**：为 workspace 配置统一容量限制
3. **rootfs 收紧**：容器 rootfs 改为只读或最小化
4. **审计日志**：记录子进程的网络访问和资源使用

```yaml
  SharedSkillRoot: ""              # 宿主机 shared skill 目录
  CommonSkillRoot: ""              # 宿主机 common skill 目录
```

| 文件 | 职责 |
|------|------|
| `cmd/claw.go` | 服务入口、HTTP/SSE 路由注册 |
